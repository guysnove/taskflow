## 4. Known limits and risks (accepted for 2.0)

| Limit | Why it's acceptable now | When to revisit |
|---|---|---|
| One instance, SQLite (ADR 0004) | the load fits one server with room (§2) | a second copy is needed: PostgreSQL, a shared cache and keys first ([scalability.md](../scalability.md)) |
| No real servers in this course; "staging" and "production" are folders on a CI runner | the deployment steps are real and scripted | when TaskFlow gets a host: the same script over SSH |
| The OTLP exporter has never sent to a real collector | configuration, not code | with the first monitoring backend |
| 11 requirements without tests (e.g. NFR-SEC-4, NFR-NOTIF-1) | listed by `tools/Traceability` | next release: one per sprint |
| 10 open technical debt items (e.g. TD-2 `ViewData` strings, TD-11 idempotency records never deleted) | each with interest and a decision ([tech-debt.md](../tech-debt.md)) | the quarterly review |
| Re-sending dead emails needs SQL | rare; a runbook step | the drill's open action: an admin command |
| One end-to-end test | the integration tests cover the server side; E2E covers one browser path | when the UI grows JavaScript |

## 5. Decisions taken in this review

- Release as **2.0.0** (Semantic Versioning: a major version, because API error bodies changed and running TaskFlow changed —
  a container image, new settings, new tables, two health endpoints. API requests themselves stay compatible.)
- The smoke test runs after every staging deploy and container build; not in production (it creates an account).
- The drill's action "keep the inner cause of an email failure" is done (`EmailOutboxProcessor.Describe`).
- Performance measurements always warm up first (found here: a cold start looked like a regression).
